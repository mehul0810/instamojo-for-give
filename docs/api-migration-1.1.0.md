# Instamojo API coexistence for 1.1.0

## Selection and migration

New installs default to API v2. A site with existing configured v1.1 credentials continues to use v1.1 for new requests until an administrator explicitly selects v2 and configures the appropriate live/test OAuth credentials and webhook salt. An explicit saved choice takes precedence over the historical `instamojo_for_give_api_version` filter; that filter still applies before an explicit choice is saved. Existing keys, tokens, and salts remain stored. Never use a v1.1 credential as an OAuth credential, and never retry a failed payment creation on another API.

Persist the selected API version and GiveWP environment on every new pending donation, along with its provider request ID and a hash of the configured account identifier. Credential changes leave a pending donation for manual review instead of silently verifying against a different account. Historical donations without that metadata are treated as v1.1; their verification uses the original legacy credentials and environment saved for them where available. Switching the new-payment selection must not prevent pending legacy donations from completing.

## Payment lifecycle

Versioned adapters own endpoints, authentication, request creation, and provider response parsing. New requests explicitly disable repeated payments; already-created historical requests can still have multiple attempts, so a later verified success may recover a failed donation. The gateway rejects non-INR forms and missing selected-environment credentials or v2 webhook salt before inserting a donation. Shared reconciliation checks the request ID, account fingerprint where recorded, transaction ownership, amount, currency, and provider status before changing GiveWP status. Both browser return and authenticated webhook use it. Repeated or delayed notifications must be idempotent. Invalid/malformed provider responses and network failures must not turn an unverified donation into a confirmed failure or success.

V1.1 stays available for existing configured sites throughout 1.1.0. The 1.1.0 settings screen explains that this plugin plans to deprecate its v1.1 integration in 1.2.0 and gives explicit v2 setup steps. The readme repeats this upgrade notice. Deprecation is not removal; the 1.2.0 plan must account for pending legacy payments before any adapter removal. No provider sunset date is asserted.

## Proof and rollout

Use isolated WordPress/GiveWP fixtures, synthetic credentials, and mocked HTTP responses for fresh v2 installs, existing v1.1 installs, explicit migration, environment separation, and pending legacy returns after migration. Cover successful, failed, duplicate, mismatched, and malformed events. Keep the public gateway ID and legacy settings unchanged. Real Instamojo sandbox responses remain an unverified integration gate; production deployment and release are outside this work.

References: [v2 request](https://docs.instamojo.com/reference/create-a-payment-request-1), [v2 payment](https://docs.instamojo.com/reference/get-payment-details-1), [OAuth](https://docs.instamojo.com/reference/generate-access-token-application-based-authentication), [v1.1 request](https://docs.instamojo.com/v1.1/reference/create-a-request), [v1.1 payment](https://docs.instamojo.com/v1.1/reference/get-payment-details), [webhook](https://docs.instamojo.com/reference/payments-api).

## Current local verification and gates

The local PHP 8.1.34 and 8.5.10 matrix passes syntax checks and seven isolated mock scripts: required fields, legacy settings, metadata lookup, versioned payment flows, API transport/cache separation, modern gateway creation, and legacy loading. The tests use provider fields from the [official v1.1 payment example](https://docs.instamojo.com/v1.1/reference/get-payment-details) and [v2 payment example](https://docs.instamojo.com/reference/get-payment-details-1). An independent review prompted corrections to the v1.1 create path and payment ID, repeated-payment setting, settings default, readme notice, token invalidation, and INR preflight.

Earlier Playground CLI runs on WordPress 6.5.13–7.1.3, PHP 7.4.33–8.3.33, and GiveWP 3.22.0/4.19.0 predated the final fixes. The CLI's `run-blueprint` invoked a listener without a host argument, so those runs are not current full-diff proof and should not be repeated. Current proof used `bootWordPressAndRequestHandler` with the PHP-WASM proxy on loopback, `WP_HTTP_BLOCK_EXTERNAL`, and a mu-plugin that blocked external HTTP except synthetic Instamojo responses.

GiveWP 4.19.0's `DonationFormRepository::getEnabledPaymentGateways()` only includes registered modern gateways supporting form version 3. `ModernGateway` retains `instamojo_checkout`, registers through `givewp_register_payment_gateway`, advertises `[3]`, and returns GiveWP's `RedirectOffsite` command. Refunds remain disabled. The original `give_payment_gateways` registration and checkout hook remain for legacy forms. The current source activated on WordPress 7.1.3/PHP 7.4.33 with GiveWP 3.22.0 and 4.19.0. Both versions registered the modern adapter and created a mocked v2 offsite redirect; GiveWP 4.19.0 also created a v1.1 redirect with synthetic legacy credentials.

The first real GiveWP donation insert failed because `wp_give_campaigns` was absent. The disposable SQLite fixture lacked GiveWP legacy tables, causing its early Stripe migration (`add-missing-transaction-id-for-uncompleted-stripe-donations`) to fail before campaign migrations. In the fixture only, GiveWP's own `give_get_tables()` creation methods built the missing tables; removing the failed migration row and rerunning `MigrationsRunner::run()` completed the migrations. This is fixture setup, not a plugin or site migration.

With those tables and a diagnostic hook moved after GiveWP's `init` setup, the current plugin created a real pending modern GiveWP Donation with INR 50 consistently present in the model and stored payment metadata. A forged v2 webhook returned 403 and left it pending; a valid MAC webhook completed it; a later browser return left it complete. Running the diagnostic hook too early had left GiveWP's currency cache uninitialized and produced a false 50-to-5 fixture amount mismatch; no plugin amount change was made. Another fixture activated the original 1.0.0 source, seeded a pending v1.1 donation with its old settings, replaced its source with the current diff, then selected v2 and created a new v2 donation. The old donation remained pending after a forged v1.1 webhook, completed from a valid v1.1 webhook, and stayed complete after a later return. Its historical record had no saved API version; reconciliation correctly used v1.1 and its stored test mode.

A real GiveWP 4.19.0 Visual Builder form was created through its model API. Its enabled gateway list included `instamojo_checkout`. Chromium loaded the public form on an owned loopback HTTP server and displayed “Donate with Instamojo” plus the adapter's redirect message. A second Visual Builder fixture used INR and synthetic v2 test credentials. With Chromium navigation to `test.instamojo.com` intercepted and fulfilled by local HTML, a synthetic donor completed the form and reached the synthetic offsite URL. No browser request reached Instamojo.

PHP 5.6 remains the published plugin-header minimum. The host has PHP 8.1 and 8.5; the installed Playground package has PHP 5.2, 7.4, and 8.x WASM runtimes, but no PHP 5.6 runtime. Legacy source and tests pass PHPCompatibility 9.3.5 with `testVersion 5.6-`. `ModernGateway.php` uses PHP 7 method signatures required by modern GiveWP and is loaded only when that framework registers its hook. The PHP 5.6-compatible `modern-loading-legacy.php` test checks that the old path does not load the class. The [GitHub Actions run for commit 20e3683](https://github.com/mehul0810/instamojo-for-give/actions/runs/38517444295) passed the mocked regression matrix on actual PHP 5.6, 8.1, and 8.3 runtimes. It does not exercise WordPress/GiveWP integration on PHP 5.6.

Historical mode gap: version 1.0.0 saved `MG_instamojo_for_give_payment_request_id` but did not save an environment or account fingerprint. Its legacy checkout called GiveWP's `give_insert_payment()` without a mode argument; GiveWP assigned the then-current `give_is_test_mode()` value and normally persisted it as `_give_payment_mode`. The provider request ID, gateway ID, amount, transaction ID, form, date, and donor do not encode which provider environment or account created the request. Current global `test_mode` is mutable, and GiveWP's model default for an absent mode also reads that current setting, so neither proves historical mode. The old plugin's return URL was the same in both environments. If `_give_payment_mode` is missing or invalid and no new per-donation environment exists, callback handling leaves the donation pending, performs no provider lookup or status mutation, and returns a pending-verification message on browser return or HTTP 503 on webhook. Regression coverage asserts both paths. The recommended bounded policy is manual reconciliation: an operator checks the original provider dashboard or trustworthy historical records, records the confirmed environment for the individual donation, and only then retries verification. A future tool for this should require explicit per-donation evidence and an audit trail; it should never copy the site's current global mode or probe both environments. Guessing could query the wrong account, fail a paid donation, or bind an unrelated payment to a donation.

Remaining gates: authorized Instamojo sandbox response and webhook delivery checks, WordPress/GiveWP integration on PHP 5.6, and a product decision on whether to build an audited per-donation manual reconciliation tool for historical missing-mode cases. The host has PHP 8.1 and 8.5; cached official `@php-wasm` Node packages include 5.2, 7.4, and 8.x but no 5.6 package, and there is no PHP 5.6 executable or container runtime installed. Actual PHP 5.6 mock tests ran in GitHub Actions; local WordPress/GiveWP integration on PHP 5.6 still requires a separately available isolated runtime. No real credentials or live payments were used. The in-process runtime, database, and browser fixtures were disposable `/tmp` diagnostics, not CI jobs.
